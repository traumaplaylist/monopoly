# Архитектура

```
packages/
  content/     карта «Мегаполис», ruleset V1 (все числа), колода «Шанс», предметы, валидатор карты
  game-core/   чистые правила: (state, seat, command, serverNow) → state + events; мини-игры; проекции; debug-боты
  protocol/    zod-схемы входящих сообщений, типы снимков, имена событий Socket.IO
apps/
  server/      Node + Socket.IO + node:sqlite: гости, комнаты, матч, таймеры, идемпотентность, восстановление
  client/      React + Vite + Three.js (React Three Fiber), DOM-интерфейс поверх WebGL
tests/e2e/     Playwright: четыре независимых браузерных контекста против реального сервера
```

Один набор правил — `@pb/game-core`. Сервер — единственный авторитет; клиент импортирует ядро только для **чтения** (вычислить аренду для подписи, кто сейчас действует), но не меняет состояние.

## Состояние матча (`MatchState`)
- Версии: `schemaVersion`, `rulesVersion`; протокол — `PROTOCOL_VERSION` в `@pb/protocol`.
- `matchId`, монотонный `revision` (растёт при каждом изменении).
- `seed` и `rng` (состояние mulberry32) — приватные, не попадают в проекцию.
- Игроки (seat IDs `s0…s3`, роль `alive/ghost/left`, деньги, позиция, предметы, жетоны, энергия призрака), `order`, `turnIndex`, `round`.
- `tiles` — слой владения (владелец, уровень, залог) отдельно от статических данных карты.
- Фаза и **абсолютный серверный дедлайн** `deadline`; текущие аукцион, сделка, вызов, дуэль (с резервом), мини-игра, долг, очередь обязательств `pending`, ловушки, запреты призраков, очередь мини-игр, пары дуэлей за раунд.
- Колода «Шанс» (порядок — приватный), журнал последних 150 событий, итог, статистика длительности фаз.

## Фазы
```
PRE_ROLL ──ROLL/таймаут──► (движение, эффекты, обязательства)
   │                           ├─► RENT_CHOICE (скидка) ─► …
   │                           ├─► DEBT ──оплата/ликвидация/банкротство──► …
   │                           ├─► PURCHASE ──покупка──► POST_ROLL
   │                           │        └─отказ/таймаут─► AUCTION ─► POST_ROLL
   │                           └─► AUCTION (угол) ─► POST_ROLL
   ├─PROPOSE_TRADE─► TRADE ─ответ/таймаут─► (возврат в PRE/POST с остатком времени)
   └─PROPOSE_DUEL─► DUEL_OFFER ─принято─► DUEL (мини-игра на двоих) ─► (возврат)
POST_ROLL ─END_TURN/таймаут─► следующий живой игрок
   └─ если круг замкнулся: граница раунда → [MINIGAME] → PRE_ROLL следующего
      └─ раунд 12 закончен или остался один живой → FINISHED
```
Каждая команда разрешена только в своих фазах (`requireTurn`, `requireManage`); остальные отклоняются с кодом ошибки.

## Время
Ядро не читает часы. Сервер передаёт `now` в `applyCommand` и `advance`; `nextDeadline(state)` даёт ближайший момент самостоятельного изменения (фаза, этап мини-игры, предмет на выбор). Сервер держит **один таймер на комнату** до этого момента. После перезапуска таймеры пересчитываются из состояния; просроченное обрабатывается один раз при загрузке, следующие фазы получают полные сроки (без каскада авто-ходов).

## Проекции
- `publicView(state)` — без `rng`, `seed`, порядка колоды, без последовательностей «Курьера» (кроме текущей во время показа).
- `privateView(state, seat)` — личные данные (предмет, ожидающий замены).
- Секреты возобновления сессии живут только в таблице гостей (как SHA-256), в снимки не попадают.

## Протокол (Socket.IO)
| Событие | Направление | Назначение |
|---|---|---|
| `session:hello` `{protocolVersion, token?, name?}` | → | вход или возобновление гостя; новый токен возвращается один раз |
| `room:create / join / ready / avatar / settings / start / leave / rematch` | → | лобби и реванш |
| `match:cmd` `{commandId, matchId, expectedRevision?, command}` | → | игровая команда |
| `sync`, `time:ping` | → | полный снимок, синхронизация часов |
| `snapshot` | ← | `{room, match (public), me {guestId, seat, private}, serverTime}` после каждого изменения |
| `session:replaced` | ← | место открыто на другом устройстве |

Все входящие данные проходят zod-схемы, размер сообщения ≤ 16 КБ, 25 сообщений/с на соединение. Личность — сессия соединения, а не `playerId` из JSON.

## Идемпотентность и атомарность
- Ключ `matchId:guestId:commandId`. Повтор с тем же содержимым возвращает сохранённый ответ (`duplicate: true`) и ничего не исполняет; тот же id с другим содержимым — `commandIdConflict`.
- Порядок: проверка → новое состояние → **запись комнаты и событий одной транзакцией SQLite** → ответ → рассылка. Если рассылка потерялась, клиент получает актуальный снимок при `sync`/переподключении.
- Результаты успешных команд хранятся вместе с состоянием комнаты (последние 600), поэтому повтор после перезапуска сервера тоже не исполняется дважды.
- Обработчики синхронные (SQLite синхронный, Node однопоточный) — команды одной комнаты не перемешиваются.

## Переподключение
- Гость = случайный UUID + 256-битный секрет (в `localStorage`, не в URL). Код комнаты — приглашение, не право на чужое место.
- Одно активное соединение на гостя: новое вытесняет старое (`session:replaced`), старое отключается и больше не может отправлять команды.
- Socket.IO connection state recovery включён как оптимизация; основной путь — `hello` + полный снимок.
- Клиент при возврате из фона отбрасывает устаревшие анимации и запрашивает снимок.
- Политика отсутствия: 5 минут без связи в матче → выход (ликвидация в банк); в лобби — освобождение места. Все отключились на 60 с → комната на паузе (сроки сдвигаются при возвращении). 30 минут — выгрузка из памяти (остаётся в базе). Хранение — 3 дня.

## Хранилище (SQLite, `node:sqlite`)
- `guests(guest_id, token_hash, name, room_id, …)`
- `rooms(room_id, code, status, data JSON, updated_at)` — полное авторитетное состояние комнаты и матча
- `match_events(room_id, match_id, revision, data, at)` — минимальный журнал событий

`node:sqlite` встроен в Node ≥ 22.13 (без нативных модулей — без проблем сборки на Windows). На Node 22 печатается ExperimentalWarning; в `npm start` она скрыта.

## Клиент
- `net/connection.ts` — сокет, `hello`, синхронизация времени (3 пинга, лучшая половина RTT), отправка команд с `commandId` (повтор того же id при таймауте).
- `state/store.ts` (Zustand) — снимок, производные анимации только по свежим событиям (< 4 с), выбор клетки, панели.
- `render/` — ортографическая камера почти сверху, профили раскладки `landscape`/`portrait` (одни и те же индексы клеток, разные координаты), клетки-блоки с canvas-текстурами, пиксельные персонажи-спрайты на подставках с отдельной тенью, low-poly улучшения и конусы. Подключаемая графика — `public/assets.json` (см. `ASSETS.md`).
- DOM-плашки на поле (баннер, подсказки) привязаны к точкам поля и пересчитываются каждый кадр без ре-рендера React.
- Мини-игры — DOM-слой, время по синхронизированным серверным часам; клиент отправляет только нажатия.
